# Agent guide: bt-portfolio

## Purpose and architecture

This is Bryan Tung's personal portfolio. Production is a static GitHub Pages site generated by `build.js`; `views/index.html` is the common layout, `views/partials/` contains page fragments, and `public/` contains copied static assets. `server.js` can render the same fragments through Express, but GitHub Pages uses the static build.

The site uses HTMX links for page transitions and CSS theme variants (`dark`, `light`, and `winamp`). The work-experience page intentionally has two presentation modes: a timeline for dark/light and a playlist for Winamp.

## Commands

- `npm install` installs dependencies.
- `npm run build` rebuilds `dist/` from views and public assets.
- `npm start` runs the static build then serves `dist/` locally.

`dist/` is generated and ignored. Do not hand-edit it; run the build after changing source files.

## Updating experience data

Experience content has one canonical source and schema: `data/experiences.json`. `render-experiences.js` validates it and generates both visual layouts, so never edit the generated cards/playlist rows individually.

To update it without local development tools, edit `data/experiences.json` in GitHub's file editor and commit the change to `main`. The GitHub Pages workflow deploys automatically. Validate the JSON and ensure every experience includes all fields and non-empty `highlights` and `technologies` arrays before committing.

The file is public portfolio content. Do not include secrets, private contact details, client-confidential information, or credentials.

## Change guidelines

- Preserve the single-source rendering pipeline for experience content. If fields change, update the data fixture, validation, both renderer outputs, and the workflow documentation together.
- Escape any externally managed text before inserting it into HTML. `render-experiences.js` currently owns that responsibility.
- Check both the standard timeline and Winamp playlist after experience-related changes, including mobile behavior.
- Keep the GitHub Pages workflow least-privileged and avoid adding cloud infrastructure for static content without a clear operational need.
- Use the existing CSS variables and theme selectors for visual work; test every theme when editing shared selectors.
- Treat `server.js` and `build.js` as separate execution paths and keep their rendering behavior aligned.

## Verification checklist

1. Run `npm run build`.
2. Confirm `dist/experiences.html` contains each job in both `.timeline-item` and `.track-row` forms.
3. Serve `dist/` and view `/experiences.html` in dark, light, and Winamp themes.
4. Inspect `git diff` so generated or unrelated local files are not included.
